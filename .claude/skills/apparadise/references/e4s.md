# E4S (Extreme-scale Scientific Software Stack)

Reference for the apparadise decision tree. **E4S is not a build source in apparadise.** The
resolver order (requester → pixi → Spack `cuda` variant → EasyBuild → CUDA port → `no-recipe`)
does not include it. This file covers what E4S is and what it offers the **Spack path**: spec
sets, a binary cache and known-good variant combinations. It does not propose E4S as a source.

Researched 2026-11-01. Sources were the e4s.io pages, the E4S 26.06 release slides, the
`E4S-Project/e4s` and `E4S-Project/e4s-cl` GitHub repos, Docker Hub tags for `ecpe4s/*`, and a
direct read of the 26.06 build-cache index at `cache.e4s.io`. "(unverified)" marks claims that
no primary source confirmed. "(observed)" marks facts read from artefacts (repo files, cache
index, Docker Hub API) rather than from documentation.

---

## 1. What it is

- E4S is a **curated, Spack-based distribution of 125+ HPC and AI packages** (26.06 slides; the
  e4s.io home page says "over 140 interoperable libraries and tools"). It started at ECP
  (Exascale Computing Project), continues under the DOE PESO/STEP programmes, and sits under the
  **High Performance Software Foundation (HPSF)**. ParaTools, Inc. sells commercial support,
  including "ParaTools Pro for E4S" cloud images.
- E4S is **not a package manager**. It is a fixed Spack checkout, a set of `spack.yaml`
  environments (one per arch × compiler × GPU flavour × GPU arch), a signed Spack binary cache
  built from them, and container images built from that cache.
- The products are HPC libraries and apps: PETSc, Trilinos, hypre, SUNDIALS, Kokkos(-kernels),
  RAJA/Umpire/CHAI, Ginkgo, MAGMA, SLATE, STRUMPACK, SuperLU-dist, heFFTe, AMReX, ADIOS2, HDF5
  plus VOLs, Caliper, TAU, VTK-m, ParaView/VisIt, GROMACS, LAMMPS, CP2K, NWChem, Quantum
  ESPRESSO, OpenFOAM, WarpX, WRF, Xyce, Chapel, Julia and others. The **full containers** also
  carry a large Python AI layer: PyTorch, TensorFlow, JAX, vLLM, SGLang, NeMo, BioNeMo,
  Megatron, transformers, Ray, CuPy, LangChain/LangGraph, MCP and more, per the 26.06 slides.
- **Release cadence:** quarterly at first (23.08, 23.11, 24.02, 24.05), now **twice a year**
  (24.11 → 25.06 → 25.11 → 26.06). GitHub release tags: v25.06 (2025-06-06), v25.11
  (2025-11-14). There is **no v26.06 tag on GitHub** (observed).
- **Current release: 26.06, released 2026-06-22.** It uses Spack 1.1.1, Ubuntu 24.04 and Rocky
  Linux 9.7/9.8 images. The slides list CUDA 13.2, ROCm 7.2.3 and oneAPI 2026.0, but see the
  CUDA caveat in §3. Docker Hub `26.06-*` tags were re-pushed on 2026-09-18 and 2026-09-24
  (observed), so a tag is **not immutable**.
- **Next: 26.11 is in preparation** (observed). Since 2026-09-30 the repo's `vars.env` sets
  `E4S_VERSION=26.11`. A 2026-08-21 commit moved it to **Spack v1.2.2**, the same Spack
  apparadise pins (`docs/stack.md`, `SPACK_REF=v1.2.2`). The repo was reorganised on 2026-07-29
  for an automated release process.

## 2. Delivery forms

### 2a. Full release containers (monolithic)

Docker Hub `ecpe4s/*` (the container-download page, sizes as of 2026-09-15). The same images
are also published as `.sif` under `https://oaciss.nic.uoregon.edu/e4s/images/26.06/`.

| Image:tag | Arches | Compressed size |
|---|---|---|
| `ecpe4s/e4s-cuda:26.06-cuda80` | amd64, arm64 | 30–34 GB |
| `ecpe4s/e4s-cuda:26.06-cuda90` | amd64, arm64 | 30–34 GB |
| `ecpe4s/e4s-cuda:26.06-cuda120` | amd64, arm64 | 31–33 GB |
| `ecpe4s/e4s-cuda:26.06-cuda70` | ppc64le only | 17 GB |
| `ecpe4s/e4s-cuda-rocky:26.06-cuda90` / `-cuda120` | amd64, arm64 (Rocky 9) | ~30–34 GB |
| `ecpe4s/e4s-cpu:26.06`, `e4s-cpu-rocky:26.06` | amd64, arm64 | 17–24 GB |
| `ecpe4s/e4s-rocm:26.06-gfx908` / `gfx90a` / `gfx942` | amd64 | 23 GB |
| `ecpe4s/e4s-oneapi:26.06` | amd64 | 24 GB |

- The tags are **multi-arch manifests** (amd64 + arm64), so the same pull works on Grace or Vera
  and x86.
- Uncompressed size is **2–5× larger** (site note). A single amd64 `e4s-cuda-x86_64` layer set
  shows 39.5 GB compressed on Docker Hub (observed).
- `ecpe4s/e4s-cuda:26.06` and `:latest` are a combined tag (amd64, arm64, ppc64le). Which
  `cuda_arch` the untagged flavour carries is (unverified).
- Each image holds a Spack install tree **plus** pip-installed AI packages, with Lmod modules
  generated by Spack (the release Dockerfile copies a `modules.yaml`, observed). The AI stack is
  **not** in the Spack cache: `py-torch` is absent from the 26.06 cache index (observed). That
  layer is built some other way, presumably pip (unverified).
- The CUDA base is **not NGC**. E4S installs the NVIDIA CUDA runfile plus cuDNN onto plain
  Ubuntu or Rocky (`container-images/2-gpu/*/Dockerfile`, observed).

### 2b. Cache-backed images (CBI) and base images

- `ecpe4s/e4s-spack-cpu`, `e4s-spack-cuda` (amd64/arm64/ppc64le, ~8 GB), `e4s-spack-rocm` and
  `e4s-spack-oneapi` contain "just Spack and MPICH", already pointed at the E4S build cache.
  You install what you need, and binaries come down instead of compiling.
- `ecpe4s/e4s-base-cuda:26.06` (5–8 GB) is the GPU SDK base without Spack products.
- `ecpe4s/ubuntu24.04-runner-{x86_64,aarch64}-gcc-13.3` and `rocky9-runner-*` are minimal CI
  runners (~1 GB).

### 2c. Spack binary build cache

- URL pattern: `https://cache.e4s.io/<release>`, e.g. `https://cache.e4s.io/26.06`. The site
  also mentions a "mixed" all-releases cache but gives no URL (unverified).
- 26.06 uses the **Spack v3 buildcache layout** (`v3/manifests/...`, observed), so it needs
  **Spack ≥ 1.0** (unverified as a hard minimum; layout v3 arrived with Spack 1.0).
- **Contents of 26.06 (observed from the cache index, 5,658 specs, 739 package names):**

  | OS | target | specs |
  |---|---|---|
  | ubuntu24.04 | `x86_64_v3` | 1,809 |
  | rocky9 | `x86_64_v3` | 1,022 |
  | ubuntu24.04 | `aarch64` (generic) | 1,051 |
  | rocky9 | `aarch64` (generic) | 925 |
  | ubuntu20.04 | `ppc64le` | 851 |

- Signing keys are published in the cache (`v3/manifests/key/...`). Trust them with
  `spack buildcache keys --install --trust`.

### 2d. `spack.yaml` environments (the "reference spec set")

- Repo: `github.com/E4S-Project/e4s`, directory `environments/`. Layout on `master` since the
  2026-07-29 reorganisation:
  ```
  environments/{x86_64,aarch64,ppc64le}/gnu/_config/packages.yaml   # compilers, target, externals
  environments/x86_64/gnu/cuda/_config/packages.yaml                # cuda external
  environments/x86_64/gnu/cuda/{80,86,89,90,120,notarget}/spack.yaml
  environments/aarch64/gnu/cuda/{80,90,120,notarget}/spack.yaml
  environments/x86_64/gnu/rocm/{gfx908,gfx90a,gfx942,notarget}/spack.yaml
  environments/x86_64/oneapi/{cpu,gpu}/spack.yaml
  ```
  The older layout, e.g. `environments/25.06/amd64-gcc-cuda-ubuntu22.04` or
  `environments/x86_64-gcc-cuda-ubuntu24.04`, lives in tags `v25.06`/`v25.11` and the snapshot
  branch `master-202607291108`.
- Each `spack.yaml` is a flat `specs:` list with `concretizer: {unify: false, reuse: false}` and
  `view: false`. **The commented-out "not installed" block, with the failure reason for each
  package, is the most useful part for apparadise.** Examples from `x86_64/gnu/cuda/120`
  (observed, 2026-10):
  - `cabana`: "Unsupported CUDA arch: 120" with kokkos 4.6.02.
  - `cp2k`: "only supports cuda_arch 35,37,60,70,80,90".
  - `dealii`: conflicts with `+cuda ^cuda@12:`.
  - `mfem`: killed (OOM).
  - `lbann`/`dihydrogen`: `CUDA::nvToolsExt` target missing.
  - `exago`: bundled fmt redefinition.
  - `paraview +cuda`: concretizer unsat.
  - `ascent`: spack issue #38045.
- `packages.yaml` conventions: `require: target=x86_64_v3` (or `target=aarch64`) on **all**,
  `gcc@13.3.0` external from `/usr`, `mpi: require: mpich`, `mpich@5.0.1` **external, not
  buildable** at `/opt/mpi/pkgs/mpich-5.0.1`, `python@3.12.14` external at
  `/opt/python/pkgs/python`, `julia@1.12.6` external, openblas (`threads=openmp`) for
  BLAS/LAPACK, intel-tbb, and a large fixed Trilinos variant set.

### 2e. e4s-cl (E4S Container Launcher)

- `github.com/E4S-Project/e4s-cl`, MIT, latest v1.0.9 (2026-06-04). Docs at
  `e4s-cl.readthedocs.io`.
- Purpose: run an MPI binary inside a container while **swapping in the host MPI**. It works
  through MPICH ABI compatibility, or CEA's **Wi4MPI** to translate between Open MPI and MPICH
  ABIs, and binds the needed host libraries into the container.
- Commands: `e4s-cl init`, `e4s-cl launch mpirun -np 4 ./a.out`, and
  `e4s-cl profile {list,create,detect,edit,select,...}`. `profile detect` records a binary's
  library and file dependencies.
- Backends in the source tree (observed): `apptainer`, `singularity`, `docker`, `podman`,
  `shifter`, `barebones`, and `host` (no container). **There is no Enroot or Pyxis backend.**
  On apparadise's Slurm (Pyxis + Enroot only), e4s-cl does not apply. The equivalent there is
  Pyxis' own `--mpi=pmix` plus Enroot hooks.
- Related tools named in the slides: `e4s-alc` (à la carte: add OS and Spack packages to an
  existing image) and `e4s-chain-spack.sh` (chain a user Spack onto the image's Spack).

## 3. CUDA specifics

- **`cuda_arch` values built: one arch per environment, never a fat binary.**
  - x86_64: `80, 86, 89, 90, 120`.
  - aarch64: `80, 90, 120`.
  - ppc64le: `70`.
  - Older releases also had `cuda75` on arm64 (25.06).

  These are confirmed both in the repo dirs and in the 26.06 cache index, which has e.g.
  gromacs 2026.1 for each of these arches (observed).
- **sm_100 / sm_103 (B200/GB200/GB300) are not built.** There is no `cuda100` image or env.
  `cuda120` means **compute capability 12.0** (RTX PRO 6000 Blackwell, RTX 50xx), not the
  datacenter Blackwell. Whether E4S's `cuda120` binaries embed PTX that would JIT on sm_100 is
  (unverified), and probably not useful anyway, because PTX only JITs forward to *newer* arches.
- **Rubin is not built.** Neither is any `f`/`a` family target. E4S uses plain numeric
  `cuda_arch`.
- **CUDA version: there is a discrepancy.**
  - The 26.06 slides say "CUDA upgraded to 13.2 (aarch64, x86_64)".
  - The 26.06 **build cache** holds `cuda@12.9.1` as an **external** at
    `/usr/local/cuda-12.9` for every x86_64 and aarch64 OS (observed).
  - The current `master` env files, preparing 26.11, also prefer the `cuda@12.9.1` external.
  - The image refs name `e4s-cuda-base-*:v12.9.1-*`, and `container-images/2-gpu` carries a
    `cuda-12_9-math-functions-newer-glibc.patch`.

  Treat the **Spack-built binaries as CUDA 12.9.1**. The 13.2 claim may apply only to the AI
  pip layer or to the image's driver-side toolkit (unverified).
- Because cuda is an *external*, any cached `+cuda` binary expects CUDA 12.9 at
  `/usr/local/cuda-12.9` at runtime and at relocation. Spack hashes the external's version and
  prefix into the DAG, so a site with a different CUDA gets **no cache hits** for `+cuda` specs.
- **Grace-Hopper / aarch64:** the arm64 CUDA images (`cuda80/90/120`) and caches are built for
  **generic `target=aarch64`** with gcc 13.3. They are not tuned for `neoverse_v2`. The slides
  label the aarch64 CPU image "macOS M-series, NVIDIA Grace". They run on GH200 and GB200, and
  `cuda90` covers H100/GH200. **There is no build for GB200's B200 (sm_100).**

## 4. Cheat sheet

```bash
# --- Containers --------------------------------------------------------------
# Enroot (what apparadise's Slurm uses). Docker Hub needs no host; another registry is docker://host#repo:tag
enroot import -o e4s-cuda120.sqsh 'docker://ecpe4s/e4s-cuda:26.06-cuda120'   # ~30 GB pull
enroot create -n e4s e4s-cuda120.sqsh
enroot start --rw e4s bash

# Pyxis on Slurm (pre-stage the .sqsh; a 30 GB pull per job is a non-starter)
srun --container-image=/path/e4s-cuda120.sqsh --container-mounts=/scratch:/scratch \
     --mpi=pmix gmx_mpi --version

# Apptainer: pull the prebuilt SIF directly, or convert from Docker Hub
wget https://oaciss.nic.uoregon.edu/e4s/images/26.06/e4s-cuda120-x86_64-26.06.sif
apptainer exec --nv e4s-cuda120-x86_64-26.06.sif bash -lc 'module avail'
apptainer pull docker://ecpe4s/e4s-cuda:26.06-cuda120

# --- Build cache from a site Spack (≥1.0) ----------------------------------
spack mirror add --scope=site e4s-26.06 https://cache.e4s.io/26.06
spack buildcache keys --install --trust
spack buildcache list -L --allarch gromacs        # what is actually there
spack install --use-buildcache only  'kokkos +cuda cuda_arch=90 target=x86_64_v3 %gcc@13.3.0'
spack install -b auto ...                          # fall back to source on a miss (-b = --use-buildcache)

# Hit-rate rules: match E4S exactly, or you rebuild from source.
#   target=x86_64_v3 | aarch64,  %gcc@13.3.0,  ^cuda@12.9.1 external at /usr/local/cuda-12.9,
#   ^mpich@5.0.1 external at /opt/mpi/pkgs/mpich-5.0.1,  single cuda_arch.
# Easiest: work inside ecpe4s/e4s-spack-cuda, which already has those externals in place.

# --- Reuse E4S's environment as a starting point --------------------------
git clone https://github.com/E4S-Project/e4s && cd e4s/environments/x86_64/gnu/cuda/120
spack -e . concretize -f | tee concretize.log      # E4S's documented flow
spack -e . install -j32
```

Check any `spack install` flag spelling against `spack install --help` for the pinned Spack.
The E4S page writes `-b only|auto|never`, which is `--use-buildcache`. **(unverified for 1.2.2)**

## 5. Limits and gotchas

- **Size.** The full CUDA images are 30–34 GB compressed and roughly 60–150 GB unpacked. A
  `.sqsh` of that on CephFS for every node is costly, and Enroot import takes tens of minutes.
  Cache-backed images (~8 GB) are the lean option.
- **Staleness.**
  - Two releases a year. The pinned versions are whatever the release Spack checkout chose.
    26.06 has gromacs 2026.1, lammps 20250722.3, petsc 3.25.2 and kokkos 5.1.1 (observed).
  - Products that fail on a new arch are **silently dropped** to the commented-out list. In
    `cuda/120` that includes cabana, cp2k, dealii, mfem, lbann, exago, paraview+cuda and ascent.
  - Release tags are re-pushed months later, so pin by digest.
- **Generic CPU targets.**
  - x86 builds use `x86_64_v3` (AVX2, no AVX-512), and arm builds use `aarch64` (Armv8.0
    baseline, no SVE or neoverse tuning).
  - That is portable but leaves performance on the table on `rtx` (apparadise uses
    `x86_64_v4`) and on Grace or Vera (`neoverse_v2`).
  - Spack does **not** reuse a `x86_64_v3` binary when the spec `require`s `x86_64_v4`.
- **Single `cuda_arch` per build.** This conflicts with apparadise `generic` (a multi-arch list
  `70…120` with PTX for 120). No E4S binary matches a multi-arch spec.
- **Externals bake in host layout.** The cached binaries depend on externals: gcc 13.3 from
  `/usr`, mpich 5.0.1, python 3.12.14, cuda 12.9.1, julia. Outside E4S images, those prefixes
  must exist and match, or Spack rebuilds.
- **MPI.** The images use MPICH 5.0.1 (ch4/OFI, `~slurm`, `~cuda`, observed). On an
  InfiniBand/Slurm cluster you need ABI-compatible host MPI injection, which is what e4s-cl
  does, and it does not support Enroot. `~cuda` mpich means **no CUDA-aware MPI** in the stock
  images (observed from the external spec string).
- **Monolithic.** One image holds hundreds of products with one MPI, one Python and one CUDA. A
  single CVE or bump means rebuilding everything, and there is no per-package provenance in the
  image.
- **Licensing.**
  - The `E4S-Project/e4s` repo and e4s-cl are **MIT**.
  - Each product keeps its own licence: GROMACS LGPL-2.1, LAMMPS GPL-2.0, Xyce GPL-3.0,
    PETSc/Trilinos BSD-style, and so on.
  - The images also redistribute NVIDIA CUDA and cuDNN under NVIDIA's EULAs. They are installed
    from the runfile and the cuDNN archive (observed).
  - Re-hosting E4S images in Zot `public` means re-distributing all of that. Licence review is
    the site's job, and E4S publishes no consolidated licence manifest (unverified that none
    exists).
- **Support.** The project is community-supported, with GitHub Discussions at
  `github.com/orgs/E4S-Project/discussions`. Commercial support comes via ParaTools.

## 6. How E4S relates to apparadise

apparadise's rules (CLAUDE.md, decided): one image, one source, one solver. **One package per
image**, tagged `<name>:<version>-<target>`. Base images derive from **NGC**. Targets are `vr`
(aarch64, CUDA 13.0.3, `neoverse_v2`), `rtx` (`x86_64_v4`, sm_120, CUDA 13.0.3) and `generic`
(sm_70–sm_120 + PTX, CUDA 12.9.2). The pinned Spack is v1.2.2.

**Where E4S conflicts:**

- The full E4S images are monolithic, hundreds of products per image. They cannot be catalogued
  as `<name>:<version>-<target>`. They do not derive from NGC, and they do not match any
  apparadise target's CUDA, CPU target or arch list. They are not candidates for the catalog,
  and must not be re-tagged as apparadise builds.
- The 26.06 binary cache hit rate for apparadise specs is effectively **zero for `+cuda`
  packages** (analysis from observed data):
  - `rtx`: `x86_64_v4` ≠ `x86_64_v3`, and CUDA 13.0.3 ≠ 12.9.1.
  - `vr`: `neoverse_v2` ≠ `aarch64`, and CUDA 13.0.3 ≠ 12.9.1.
  - `generic`: multi-arch `cuda_arch` ≠ single arch, and 12.9.2 ≠ 12.9.1.

  Pure-CPU leaves that don't depend on MPI or Python externals could hit on `generic`, but only
  with `%gcc@13.3.0` and only if the builder's OS matches. Measure with
  `spack buildcache list` before relying on it.
- Adding `cache.e4s.io` as a mirror on builders pulls third-party signed binaries into images
  that apparadise signs as its own. That is a supply-chain and trust decision for the owner.
  **Ask in QUESTIONS.md; do not add it.**

**Where E4S helps (reference only, no repo change implied):**

- **Spec reference.** The `environments/*/gnu/cuda/{90,120}/spack.yaml` files are a
  continuously tested list of "this `+cuda` variant set concretises and builds with Spack
  1.1–1.2 for cuda_arch 90/120 on x86_64_v3 and aarch64". Use them to pick variants when
  writing an apparadise Spack spec (`--spec` for `apparadise.recipes`). For example:
  - `lammps` with the long `+package` list,
  - `petsc +metis +hdf5 +hypre +superlu-dist +cuda`,
  - `kokkos +wrapper +cuda`,
  - `chapel +cuda ^llvm targets=x86,nvptx`.
- **Failure foreknowledge.** The commented-out "not installed" block in the `cuda/120` envs is a
  ready list of known sm_120 and CUDA 12.x breakages (cp2k's cuda_arch whitelist, kokkos 4.6
  rejecting 120, dealii vs `cuda@12:`, mfem OOM, the dihydrogen nvToolsExt removal). Check it
  before a `concretize` or `build` failure lands in the public failure DB. It is also useful for
  `recipes/repairs.yml` patterns. The 26.11 env is being updated now; read it from `master`.
- **sm_120 evidence for `rtx`.** E4S shows which HPC libraries already build for compute
  capability 12.0: gromacs, lammps, petsc, hypre, ginkgo, magma, trilinos, kokkos 5.1.1, raja,
  umpire, slate, sundials, superlu-dist, heffte, adios2, vtk-m and others (observed in the cache
  index). This makes them good first candidates for the `rtx` Spack path.
- **Quick user sandbox (outside apparadise).** A user who wants "the whole ECP stack" now can
  `enroot import` an `ecpe4s/e4s-cuda:26.06-cuda120` (rtx) or `-cuda90` (GH200) image
  themselves. That is not an apparadise product.
- **Vera Rubin / datacenter Blackwell.** E4S has nothing for sm_100/sm_103 or Rubin, and nothing
  tuned for Grace or Vera. E4S cannot help answer Q13 (Rubin CC, Vera archspec target). Expect
  E4S to lag new arches by at least a release, as `cuda120` first appeared in 25.11.

## 7. Decision-tree guidance

**Consult E4S when:**

- writing or debugging a **Spack** spec for an HPC library or app that E4S ships (PETSc,
  Trilinos, hypre, SUNDIALS, Kokkos, RAJA, AMReX, ADIOS2, LAMMPS, GROMACS, Ginkgo, MAGMA, SLATE
  and others), to borrow a variant set that is known to concretise;
- a Spack build fails for `cuda_arch=120` or `90`, to check E4S's commented-out list for the
  same failure and its cause;
- judging whether a library is **sm_120-ready at all** before queueing an `rtx` build;
- a user asks for a broad "ECP software stack" sandbox and accepts a 30 GB third-party image
  outside the catalog (point them to E4S; don't build it);
- comparing Spack versions or variant drift: E4S `master` tracks Spack v1.2.2, like apparadise.

**Do not use E4S when:**

- you need an apparadise **catalog image**. E4S images are monolithic, non-NGC and multi-product,
  which violates one package per image;
- the target is `vr` (Rubin CC unknown, generic `aarch64` only, no `neoverse_v2`), or any
  sm_100 or sm_103 GPU;
- the package is in the AI/Python layer (PyTorch, vLLM, JAX, NeMo). Those are not Spack-built in
  E4S and come from pixi or conda-forge in apparadise's resolver;
- you want cache hits for `rtx` or `generic` builds. CUDA version, CPU target and `cuda_arch`
  shape all differ (§6);
- the Slurm path needs MPI injection: e4s-cl has no Enroot or Pyxis backend;
- licence or provenance must be per-package and signed by apparadise;
- you would add E4S as a new resolver source. That is not decided; put it in `QUESTIONS.md`.
